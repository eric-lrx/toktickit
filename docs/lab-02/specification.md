# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver the Requester-facing slice of TokTickIT: a Development Requester can select an
identity, create a support ticket with attachments, find it again in My Tickets, open
its read-only Ticket Detail, and manage its attachments — all scoped so one Requester
never sees another Requester's data.

## 2. Stakeholder Request Interpretation

IT wants a working ticket intake path before real login exists. A Requester picks a
seeded test identity, describes a problem (category, related system, priority,
summary, description), attaches evidence, and submits. Afterwards they must be able to
find, filter, and re-open their own tickets and manage attachments, with the backend
guaranteeing they can never reach another Requester's data. The Development Requester
selector explicitly stands in for login until Lab 3.

## 3. Scope

### Included
- Development Requester Selection screen, selection persistence, and Change Requester
- Create Ticket (validation, ticket number generation, attachment upload)
- My Tickets (search, filter, sort, pagination, empty/no-results/failure states)
- Requester Ticket Detail (read-only)
- Attachment lifecycle: add, download, soft-remove with reason
- Ownership enforcement on every requester-scoped read and write
- Zen Green application shell and reusable UI components

### Excluded
- Authentication, sessions, passwords, tokens, real authorization (BR-03)
- IT Staff workflow: queue, claiming, IT Priority, Ticket Owner
- Public Comments, Internal Notes, Actions Taken
- Any ticket status beyond `NEW` (no resolve/close/reopen/cancel)
- Administration of users, Requesters, or reference data

## 4. Functional Requirements

- **FR-01** A Requester selects an active Development Requester before any ticket
  feature is reachable.
- **FR-02** A Requester can change the active Development Requester at any time.
- **FR-03** A Requester can create a Ticket with all required fields and zero or more
  attachments.
- **FR-04** The system generates a unique, backend-issued Ticket Number on successful
  creation.
- **FR-05** A Requester can list their own Tickets (My Tickets).
- **FR-06** A Requester can search their Tickets by Ticket Number or Summary text.
- **FR-07** A Requester can filter their Tickets by Category, Related System, and
  Requested Priority.
- **FR-08** A Requester can sort their Tickets by `createdAt`, `ticketNumber`, or
  `summary`, ascending or descending.
- **FR-09** A Requester can page through their Tickets with a selectable page size.
- **FR-10** A Requester can open the Ticket Detail of a Ticket they own.
- **FR-11** A Requester can add an Attachment to a Ticket they own.
- **FR-12** A Requester can download an active Attachment they own.
- **FR-13** A Requester can soft-remove an Attachment they own, supplying a reason.
- **FR-14** The system rejects any attempt to create, read, or modify a Ticket or
  Attachment not owned by the current Requester.

## 5. Business Rules

- **BR-01** The official Ticket Number is generated by the backend and must be unique.
- **BR-02** A new Ticket begins with Current Status `New`.
- **BR-03** The Development Requester selector is a testing mechanism for Lab 2 only;
  it is not authentication and grants no real security guarantee.
- **BR-04** Ticket Number format is `TKT-YYYY-NNNNNN`, sequential per calendar year,
  generated inside a database transaction with retry on unique-constraint collision so
  two concurrent creations never produce the same number.
- **BR-05** `id`, `ticketNumber`, `requesterId`, `createdAt`, `updatedAt` are
  system-generated; the Requester cannot set or edit them.
- **BR-06** The selected Requester id is stored client-side in `localStorage`
  (`toktickit.requesterId`) and sent via the `X-Dev-Requester-Id` header on every call
  that needs requester context.
- **BR-07** A missing or inactive `X-Dev-Requester-Id` on a protected route returns
  `400` with a message naming the problem; the frontend redirects to the selector.
- **BR-08** Switching Requester reloads all requester-scoped data; nothing from the
  previous Requester remains visible.
- **BR-09** A Ticket is owned by the Requester referenced in its `requesterId`. An
  Attachment inherits ownership from its Ticket.
- **BR-10** A Ticket or Attachment request that exists but is not owned by the current
  Requester returns `404`, identical to a truly nonexistent resource, so existence is
  never leaked by the response code (see §11 for justification).
- **BR-11** My Tickets is filtered by the current Requester on the backend only; the
  frontend never receives another Requester's rows to filter out.
- **BR-12** Ticket Summary (5–150 chars) and Description (10–4000 chars) are required,
  trimmed of leading/trailing whitespace, and validated on both frontend and backend.
- **BR-13** The Submit button is disabled for the duration of an in-flight request so a
  duplicate click cannot create two Tickets.
- **BR-14** On a failed ticket-creation request, all entered field values are preserved
  and remain editable; no partial Ticket or Attachment is persisted.
- **BR-15** Allowed attachment types are JPG/JPEG, PNG, WEBP, PDF; max size 5 MB per
  file; max 5 **active** attachments per Ticket.
- **BR-16** A soft-removed attachment does not count toward the 5-active-attachment
  quota, so a Requester can remove one and add a replacement.
- **BR-17** Attachment files are stored on disk under a generated UUID + validated
  extension; the Requester-supplied filename is stored only in the database
  (`originalName`) and is never used as a disk path, to prevent path traversal.
- **BR-18** Removing an attachment requires explicit confirmation and a non-empty
  reason; only the owning Requester (via their Ticket) may remove it.
- **BR-19** A removed attachment's metadata remains visible on the Ticket; its download
  endpoint returns `404` and its preview is disabled in the UI.
- **BR-20** If Ticket creation succeeds but writing an attachment fails, the whole
  operation is rolled back: no orphaned Ticket and no orphaned file remain (compensation
  strategy, §7).
- **BR-21** An inactive Development Requester is excluded from `GET /api/requesters`
  and is rejected with `400` if its id is ever sent via the header.
- **BR-22** My Tickets distinguishes "no tickets exist yet" (empty state) from "filters
  matched nothing" (no-results state); they use different messaging.
- **BR-23** `TicketStatus` declares only `NEW` in Lab 2. No status-change endpoint or
  Current Status filter exists; both arrive in Lab 3 (see §11).
- **BR-24** IT Priority and Ticket Owner are out of scope for Lab 2: not in the schema,
  not in the UI, not in any API response.
- **BR-25** The Development Requester mechanism is a placeholder for Lab 3
  authentication. The `requesterId` foreign key on Ticket is designed to survive that
  migration unchanged (see §7 and §11).

## 6. UI Specification Summary

Full detail in `ui-spec.md`. Summary: a Zen Green application shell (header, nav,
current-Requester display, Change Requester) wraps four screens — Requester Selection,
Create Ticket, My Tickets, Ticket Detail. Reusable components: form field (label +
control + inline validation message), priority/status badge, loading/empty/no-results/
failure placeholders, and a responsive list that renders as a table ≥ 992px and as
cards < 768px. Every screen implements initial, loading, and failure states; Create
Ticket additionally implements validation and submitting/success states.

## 7. Data Changes

New/updated Prisma models:

| Model | Fields |
|---|---|
| `RequesterUser` | `id`, `name`, `email` (unique), `isActive`, `createdAt` |
| `Category` (existing) | + `isActive` (default `true`) |
| `RelatedSystem` | `id`, `name` (unique), `isActive`, `createdAt` |
| `Ticket` | `id`, `ticketNumber` (unique), `requesterId` FK, `categoryId` FK, `relatedSystemId` FK, `summary`, `description`, `requestedPriority` (enum `LOW\|MEDIUM\|HIGH`), `status` (enum, default `NEW`), `createdAt`, `updatedAt` |
| `Attachment` | `id`, `ticketId` FK, `originalName`, `storedName`, `mimeType`, `sizeBytes`, `uploadedAt`, `removedAt` (nullable), `removalReason` (nullable) |

Relationships: one `RequesterUser` → many `Ticket`; one `Ticket` → many `Attachment`;
one `Category` → many `Ticket`; one `RelatedSystem` → many `Ticket`.

Indexes: `Ticket.requesterId` (every My Tickets query filters on it),
`Attachment.ticketId`, unique index on `Ticket.ticketNumber`, index on
`Ticket.createdAt` (default sort). Justification (required by §5.2 of the handout): the
`requesterId` index is the one that matters most for correctness *and* performance,
because every list query is unconditionally scoped by it (BR-11) — without it, My
Tickets degrades to a full table scan under a Requester filter as ticket volume grows.

Migration path to Lab 3: `itPriority` and `ticketOwnerId` are **not added** in Lab 2.
When Lab 3 introduces them, they will be added as nullable columns with no default
tied to existing rows, so the migration is purely additive and non-destructive to Lab 2
data. `RequesterUser` is expected to be superseded or linked to a real `User` model in
Lab 3 without changing the `Ticket.requesterId` FK target's meaning.

Attachment storage: files live on disk under `server/uploads/` (added to
`.gitignore`), named `<uuid>.<validated-ext>`. `Ticket.status` enum currently declares
only `NEW` (BR-23).

## 8. API Contract

Full detail in `api-spec.md`. Summary of endpoints:

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/categories` | active categories |
| GET | `/api/related-systems` | active related systems |
| GET | `/api/requesters` | active Development Requesters |
| POST | `/api/tickets` | create a Ticket (+ optional attachments) |
| GET | `/api/tickets` | paginated, filtered, sorted list owned by current Requester |
| GET | `/api/tickets/:id` | one owned Ticket with its attachments |
| POST | `/api/tickets/:id/attachments` | add attachment(s) to an owned Ticket |
| GET | `/api/attachments/:id/download` | download one active, owned attachment |
| DELETE | `/api/attachments/:id` | soft-remove one owned attachment (reason required) |

Every route except the three reference-data GETs requires `X-Dev-Requester-Id`.

## 9. Acceptance Criteria

- **AC-01** Given valid Ticket data, when the Requester submits Create Ticket, then one
  Ticket is saved and the backend-generated Ticket Number is displayed.
- **AC-02** Given no Development Requester is selected, when the user opens My Tickets
  or Create Ticket, then the Requester Selection screen is shown instead.
- **AC-03** Given Requester B is selected, when a Ticket belonging to Requester A is
  requested by id, then `404` is returned and no Ticket data is exposed.
- **AC-04** Given the Summary field is empty, when the Requester submits, then a
  field-level validation message appears and no API call is made.
- **AC-05** Given the backend is unreachable, when the Requester submits a valid form,
  then a safe failure state is shown and all entered values remain in the form.
- **AC-06** Given a Requester has zero Tickets, when they open My Tickets, then the
  empty state is shown, not the no-results state.
- **AC-07** Given a Requester has Tickets but the applied filters match none, when My
  Tickets loads, then the no-results state is shown, not the empty state.
- **AC-08** Given a `search` value matching a Ticket Number, when My Tickets is
  queried, then that Ticket is included in the results.
- **AC-09** Given `categoryId`, `relatedSystemId`, or `requestedPriority` filters, when
  applied together, then only Tickets matching all of them are returned.
- **AC-10** Given `sort=ticketNumber&order=asc`, when the list is requested, then
  results are ordered accordingly with `id desc` as a stable secondary key.
- **AC-11** Given `page=2&pageSize=10`, when 15 Tickets exist, then the second page
  returns the remaining 5 and `meta.totalPages` equals 2.
- **AC-12** Given an invalid query parameter (e.g. `sort=nope`), when the list is
  requested, then `400` is returned naming the offending parameter.
- **AC-13** Given a Ticket owned by the current Requester, when 5 active attachments
  already exist, then a 6th upload is rejected with `409`.
- **AC-14** Given a Ticket with one active and one soft-removed attachment, when a new
  attachment is uploaded, then it succeeds because the removed one does not count
  toward the quota.
- **AC-15** Given an attachment is soft-removed with a reason, when the Ticket Detail
  is reloaded, then the attachment's metadata is still visible but its download link
  returns `404`.
- **AC-16** Given a `.exe` file is selected for upload, when the Requester attempts to
  attach it, then it is rejected client-side and, if forced, server-side with `415`.
- **AC-17** Given a 6 MB file is selected, when upload is attempted, then it is
  rejected with `413`.
- **AC-18** Given the active Requester is switched from A to B, when My Tickets
  reloads, then Requester A's Tickets are no longer visible.
- **AC-19** Given the viewport is < 768px, when My Tickets is open, then the list
  renders as cards with no horizontal scrolling.
- **AC-20** Given an inactive Requester id, when it is sent as `X-Dev-Requester-Id`,
  then the request is rejected with `400`.

## 11. Assumptions and Decisions

- **Status scope.** The handout's figures show In Progress/Resolved/Pending and a
  Current Status filter, but BR-02 and §4.2 restrict Lab 2 to ticket creation with no
  status transitions. Decision: `TicketStatus` enum declares only `NEW`; the Current
  Status filter is not implemented; later statuses are deferred to Lab 3.
- **IT Priority / Ticket Owner.** Shown in mockups but belong to the IT Staff workflow,
  explicitly excluded (§4.2). Decision: not modeled in the database or UI in Lab 2; the
  Lab 3 migration path is additive nullable columns (§7).
- **Product name.** Mockups show "TikTockIT"; the written brief says "TokTickIT".
  Decision: use **TokTickIT** everywhere.
- **Client test path.** The handout is inconsistent (§9.1 example path vs. §12
  directory listing). Decision: `client/tests/lab-02/`, consistent with the Lab 1
  convention (`client/tests/lab-01/`); `tests.md` points to the real paths.
- **Ownership response code.** Chose `404` over `403` for both Tickets and Attachments
  not owned by the current Requester, because a `403` would confirm the resource exists
  under a different owner — an information leak the ownership model must not create.
- **Compensation strategy for ticket + attachment creation.** Order of operations: (1)
  validate all files (type, size, count) before any write; (2) write files to disk
  under temporary names; (3) create the `Ticket` and `Attachment` rows in one DB
  transaction; (4a) on success, rename temp files to their final stored names; (4b) on
  failure, delete the temp files and roll back the transaction. Result: no orphaned
  Ticket row and no orphaned file on disk in either outcome.
